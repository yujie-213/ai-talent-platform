## 已确认的技术决定
本次启动补充（2026-11-05）：用户明确要求本人账号公开仓库，覆盖默认私有约定；已创建 yujie-213/ai-talent-platform。仅代码、设计与合成测试输入入库，秘密/原文件/本机数据仍排除。核实后以本机 MySQL 8.4.11 / Redis 6.2.24 固定摘要创建独立卷/端口，不升级原有服务；Windows 使用 Anaconda Python 3.13.5 的项目隔离环境。

- D01 模块化单体；FastAPI API 与独立 Celery Worker 共用业务代码。
- D02 Vue 3、TypeScript、Element Plus；FastAPI、SQLAlchemy、Alembic、MySQL；Celery/Redis；Milvus；LangGraph。
- D03 文件先使用受保护本地目录与持久化卷，原文件访问必须后端鉴权。
- D04 学习电脑 Windows + Docker Desktop；Conda 管理 Python，前后端本机开发，后台 Worker/OCR 使用 Linux 容器。
- D05 生成模型调用 API，具体服务与模型待本机配置；Embedding 本地优先复用 Ollama bge-m3，预计 1024 维，实施验证；OCR 以本地 PaddleOCR、CPU 为初始方案，版本和效果待样本验证。
- D06 一个账号最多绑定一个人才，一个人才最多绑定一个账号，也可不绑定。账号禁用不删除人才履历。
- D07 来源材料与当前有效档案分层；人工确认字段后续抽取仅提出更新建议，不自动覆盖。
- D08 同名/相似履历不自动合并；身份线索重复由 HR 对比确认关联。明确人才详情上传也应检查身份冲突。
- D09 功能权限与对应数据范围绑定授予；查看范围不被修改操作借用。默认拒绝，无复杂显式拒绝继承。
- D10 员工仅本人获授权档案，可看本人联系方式；HR 在已授权人才范围内默认完整可见联系方式，无须额外申请。其他角色按职责配置，系统管理员不自动拥有业务资料读取权。AI 证据和原文件执行同样边界。
- D11 受保护请求查询当前账号/授权，V1 不先引入权限缓存，禁用撤权后不能依赖 JWT 静态角色继续访问。
- D12 API 正常 HTTP 状态码 + 稳定业务错误码 + 追踪编号；长任务返回编号和进度查询；聊天流式输出，长语义评估返回任务卡片；断线不自动重做业务。
- D13 创建任务与待投递记录同事务；投递失败补发；幂等键按用户/操作限定，执行版本控制迟到结果。
- D14 任务、执行尝试、业务成果、LangGraph 检查点分别建模；业务状态和技术结果分别记录。
- D15 测评支持单选/多选/判断、保存草稿；多选完全正确得分，其余零分；未答零分，提交前提示。
- D16 试卷发布保存快照；提交锁定答案，唯一最终成绩；评分失败重试评分。员工看本人成绩/维度，不返回标准答案；HR 按权限查看。
- D17 V1 测评分数补充档案，不自动加入岗位匹配分；雷达图仅展示实际测量且可比较维度。
- D18 档案统一聊天使用受控查询计划；范围显式、追问继承、歧义澄清、空选不扩大；结构化全量计数不以 top-k 替代。
- D19 语义全量人数需要定义判据、对范围逐人评估，提供覆盖进度和未知项；非全量检索只报告当前找到结果。聊天只读。
- D20 交接依托 GitHub 私有仓库，所有 Agent 遵守 AGENTS.md；按文档入口和相关提交按需阅读，任务结束同步记录、提交和推送；阶段由用户与星星验收。

## 已确认的产品变更（覆盖原 PRD 对应约定）
### CR01 公司岗位、部门岗位、招聘需求分开
目的：同名同要求岗位可属于不同部门，并为后续部门缺口提供关联基础。
- 公司岗位是基础定义；部门岗位表示某部门设置的岗位；招聘需求绑定部门岗位，保存本次招聘要求及版本。
- 建岗页面先选部门及其岗位，无基础资料时由获授权人员维护；基础维护纳入 V1。
- 原 PRD“岗位草稿/有效/停用、版本与匹配”的业务规则，在本设计中应用到招聘需求。
- 现有内部员工可关联部门岗位；具体岗位基础维护采用最小必要表单，不提前做编制管理。
- 部门缺口看板仍属于后续版本，需要目标编制及实际在岗口径。不能用招聘需求数量假充缺口。
影响：基础资料、岗位表单、模型、匹配快照及权限；后续需验收跨部门同名岗位彼此独立。

### CR02 匹配默认覆盖全部授权外部候选人，可选包含内部员工
目的：避免漏选或不同岗位名称造成漏筛，支持内部紧急补位参考。
- 默认按招聘条件筛选全部授权外部候选人；不要求先关联招聘需求。
- 可选择外部候选人 + 授权内部员工，排除当前已在目标部门任职者。
- 范围在启动时固定，可加明确筛选条件；无结果或空选择不自动扩大。
- 不按原应聘岗位名称/职业名称默认排除；匹配不自动建立应聘关系。
- 用户要求全范围处理时，每位范围内人才有结果或明确失败，不用向量 top-k 代替全范围评估。
- 内部匹配仅推荐和解释，不实施调岗、转部门或审批手续。
- 列表以匹配分排名为主，硬条件/未知以标签和筛选显示；明确不满足必备条件不混入合格榜。默认合格/待核对/不满足的可见规则应在详细接口中明确，保证不满足者不以高分伪装合格。
影响：匹配范围、内部员工部门数据、列表和验收。更换人员 ID/任务 ID 不能越权。
原先讨论的“默认已关联岗位名单”未采用，以本条为准。

### CR03 技能按简历声明识别
目的：画像支持筛选，不替代后续面试评估实际水平。
- 技能栏声明 Python 或项目中使用 Python，均可作为具备 Python 技能的匹配依据。
- 保留证据，不要求必须有项目才命中，也不从出现次数推断熟练度。
- 明确“三年 Python 经验”等时间条件仍需时间依据；没有依据标未知，不能编造。
影响：标签抽取、查询和匹配规则及测试样本。

## 第二阶段实施决定（2026-11-05，既有授权范围内）
- D21 使用确定性流水线与已有MySQL执行版本/租约恢复；无需新增LangGraph检查点或数据库。OCR以独立Python子进程隔离依赖，仍属于同一Worker部署，不新增OCR微服务。
- D22 采用CPU移动版PP-OCRv5。Windows合成评测与Linux Worker真实解析/恢复均验证；不代表复杂版式或模糊件的准确率承诺。库/模型锁见technical-design.md和requirements-ocr.lock.txt。
- D23 保守保护人工确认列表：同类别存在确认事实时，新差异只作为建议，HR核对后编辑；不靠字符串相似度自动改写列表实体。手机号比较归一化空格/符号和中国区号，邮箱忽略大小写；同名仍不触发合并。
- D24 文件限额与批次失败元数据持久化；无效文件不保存正文。普通导入先建立清楚标记的待解析行，候选人视图排除尚无有效资料的占位行；明确关联保留原有档案。
- D25 MySQL事件加独立indexer进程（共享业务代码和已有MySQL，不是新服务架构）；默认30秒补偿，Strong可见确认后就绪。既有档案自动补齐索引事件，并有按当前权限/版本请求重建接口。

第二阶段审查实施补充：完整人工表单确认5类事实的当前集合，包括清空；用持久化确认记录保存该意图，不以“还存在Fact行”为判据。新迁移保守回填历史人工确认，既有明细不自动删除。索引调度使用持久化到期时间和领取版本，不新增消息队列或工作流基础设施。
