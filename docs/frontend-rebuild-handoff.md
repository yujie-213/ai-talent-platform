## 最新明确反馈（实施约束）
1. **简历筛选改用紧凑的列表/表格：一位人才一行、多列展示。** 用户明确说卡片太占空间。这覆盖前轮“候选人以卡片为主”的选择，也覆盖当前原型卡片方案。需要方便批量浏览、比较、勾选和翻页，而非把卡片缩小继续堆。
2. **人才画像、选人、问答的整体组织不合理，需要重新设计。** 当前常驻三列把名单、详情、问答同时挤压，不能原样落地。
3. **岗位与匹配页同样需要重做。** “岗位概览 / 匹配结果 / 版本历史”几个入口太不显眼，当前细弱文字页签无法承担工作区主导航；需要清楚的分区与活动状态，不能仅加深字色应付。
4. **“发起新匹配 / 查看已有结果 / 查看历史快照”等操作的位置不合理。** 用户明确否定它们挤在概览下方的布局。应按当前岗位、版本、状态与所处工作步骤安排主次操作；已在匹配页就不再堆多个语义重复的“查看结果”按钮。具体呈现随设计完善，而非死抄现有位置。
5. **普遍“上半屏太空，下半屏太挤”。** 这是跨页面问题：大标题、说明、搜索、重复状态、版本提示占掉首屏，真正的表格/履历/结果/聊天阅读区被压缩。应整体压缩顶部非关键占用，提高业务区有效面积和信息密度，避免多个嵌套滚动容器。
6. **实际可操作性优先。** 已经发生聊天发送按钮被裁切的问题，不能只证明DOM存在或toBeVisible；要检查完整处于视口/裁切祖先内、鼠标实际命中，以及长回答、放大显示、短窗口下能操作。
7. **只做需求文档和已确认变更内的功能。** 原型里延期、不做的能力不用管，不需要为追求像原型而做假数据面板、空模块或虚构AI效果。

## 已讨论的设计方向（供下一轮深化，不冒充逐项验收）
以下来自助手对用户截图的分析，用户随后要求结合今晚反馈综合重构；具体控件形式仍需合理设计，不把建议当成每项已经定稿：

- 找人/选人使用足够宽度的列表，点击查看与复选加入比较是两种操作，范围与选中数量清楚。
- 查看单人画像时聚焦完整资料；人才名单可以收起或作为返回结果/上一位下一位的辅助，不长期占据一大列。
- 概览先呈现真实关键履历与重点项目，事实、来源、测评清楚分区；减少嵌套页签，把版本/历史/诊断降为次级信息。
- AI在资料旁按需展开/收起；对话区有足够阅读面积，输入/发送固定可达。范围提示简洁且明确，不重复展示；单人示例与单人资料一致。
- 多人比较从勾选/筛选结果自然进入，给比较和回答足够空间；切换正在阅读的人不静默改变多人问答范围。问答仍复用同一套服务与会话逻辑，不要求HR选择SQL/RAG等技术模式。
- 匹配结果列表与选中人才解释就近/并列，编辑、结果、历史分开组织，保留一个统一岗位表单及JD辅助。
- 员工以本人档案/待答/成绩为中心；管理员在管理域内操作，不显示无权业务正文；HR使用业务工作区。清除测试成功/失败、裸UUID、索引维护等在常规业务中的不合理主入口。
- 默认从业务信息与步骤组织页面，再确定展示数据契约。现有API缺少需求内展示数据时可以做必要受控薄适配，不能以“不造数”为由直接删需求；不擅改评分/匹配规则、权限语义或架构。
