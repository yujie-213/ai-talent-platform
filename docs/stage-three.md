## 业务规则

- 需求绑定一个不可更换的部门岗位；跨部门新建需求，避免历史正文转移。编辑有效需求只改草稿；HR确认后追加有效版本。停用不改变已开始任务的快照，禁止新建匹配。保存需求不自动启动匹配。
- 生效必填名称、地点、薪资、职责、任职要求及结构化条件，福利可空。薪资明确区间或显式面议；币种CNY/USD/EUR，周期月/年/时；区间下限≤上限。正文中可直接识别的“优先/加分/非必备”与结构必备矛盾会阻止生效；复杂语义仍由HR确认，代码不宣称理解所有矛盾。
- 结构化条件包括必备/加分技能、最低学历、最低总工作年限、每项必备技能最低年限。技能空清单、学历“ 不限 ”、年限null/清空显式表示不限制；技能与年限不推断实际熟练度。技能年限清单只能引用必备技能。
- `requirement.read/write`分别按global或department授权；人才仍按既有`talent.read`/`task.run`范围取交集执行。管理员没有默认需求/人才正文权。创建/编辑/发起匹配需要需求当前读写；查看历史需要需求读，逐人结果/计数另按当前人才读权限过滤。
- 默认全部授权有效外部档案，不要求应聘关联，不按职业/原应聘岗位名称排除；include_internal=true时加授权内部员工，排除目标部门现任。可显式传skill或selected_ids；[]保持空范围。全部实际范围在启动事务中固定，后来新增人才不加入。任务不会自动创建应聘关系或实施内部调岗。
- 人才行与当前事实以短事务锁定后形成快照；推理不持有数据库事务。每个片段发给本地模型前、成果提交时、最终排名时复查当前执行权限。返回任务/历史/结果时重新鉴权。历史资料更新标旧，不改写结果；原文引用另检查当前文件读权与Task/File归属，失效引用不显示。

## 可解释规则v3（年限审查后）

当前版本`evidence-bm25-dense-rrf-v3`。v2曾新增技能年限，v3修复上下界/否定、总/技能归属和JD数值证据；v1/v2历史保留并标记rules_stale，不用新版算法冒充旧版重试。详细复现/验证/限制见stage-three-review.md。

1. 必备技能：技能栏声明或项目/经历明确使用均可命中；英文边界避免SQL命中NoSQL，允许中文紧邻技术名。无依据为待核对，明确否定为不满足，矛盾为待核对。这里只做保守字面规则，不虚构同义词/熟练度。
2. 学历：从教育事实中取有记录的最高已完成学历；在读/肄业不当成已获学历。低于最低条件为不满足，缺失为待核对。
3. 总年限：仅通用总工作年限声明，不能截取技能工作经验；上下界保留，只有整个区间可支持判断才判满足/不满足；工作日期区间按月合并去重，只证明下界，片段日期不足不能证明总经历不满足。冲突/缺失为待核对。中文数量词、复杂日期表述等未可靠解析时不猜。
4. 技能年限：保留上下界和否定/模糊上下文，只用明确的技能时间声明，如“Python开发经验：3年”“3年Python经验”。总工作年限、同一段工作日期和出现次数均不能代替；无明确时间为待核对。不推算真实掌握年限。
5. 全部快照事实按1200字符切片，逐人用本地锁定bge-m3（1024维）计算真实余弦相关性，取最高3片平均；整个启动范围用BM25计算词项信号，再按稠密/BM25两路全范围名次作RRF（常数60）。不用全局向量top-k代替人才全集。MySQL为权威源；此链路直接对固定快照做Embedding，不依赖Milvus当前索引就绪，也不修改其集合/模型。
6. 初始可配置权重：硬条件证据覆盖50、加分项20、语义RRF30，总计100且语义至少1；没有对应条件的项不参与并重新归一。每次启动保存权重、版本、模型标识/摘要/维度和评估日期。3条标注语义样本提供初始效果基线，不宣称权重最优或总体准确率。
7. 缺失事实在分数中表现为证据不足，三态标签同时显示；明确不满足单独分组，不进入合格组。执行失败不产生完整分数，可保留已完成的硬条件检查，不能混成合格。分数仅供本次范围内排序，不代表能力、录用概率或跨批次绝对可比的数值。解释由代码直接引用检查结果和证据，无另一次不可靠的模型自由编写，也不将测评分数混入。

## 可靠任务与接口

新增迁移`g195bb36d007`接`f084aa25c006`；新增match_runs、match_entries、match_attempts、match_outbox、talent_requirements。不改写共享迁移，不在启动建表。已应用本机开发库。沿用同一Celery/Redis和dispatcher，无新服务/检查点数据库。

- POST /api/requirements/{id}/matches：202；传version、include_internal（默认false）、skill、selected_ids（默认null）、rules；必须Idempotency-Key。固定快照，不自动扩大空范围。
- GET /api/requirements/{id}/matches：历史分页，offset/limit默认20最多100。
- GET /api/matches/{id}：状态、业务结果、当前可见进度、执行尝试、需求状态/过期、规则与需求快照。selected_ids不原样回显给其他读者。
- GET /api/matches/{id}/results：同样分页；group可为pass/unknown/fail/failed/pending或空。默认满足→待核对→不满足→失败/未完成，各组分数降序；相同分数稳定排序。
- POST /api/matches/{id}/retry：发起人传执行version，仅重试可恢复失败；成功条目和原范围/快照保留。拒绝已撤权、资料空、模型空间变更等永久失败的原任务重试；可补资料后新建任务。
- PUT /api/requirements/{id}/talents/{talent_id}：{talent_version,linked}，需要需求读写及人才读写；行锁下幂等关联，版本冲突409；应聘关系不改职业/部门/档案事实。
- GET /api/candidates增加可选requirement_id：只筛选显式关联人才，仅展示该需求的已有结果。默认未关联者仍在候选人列表，并参加默认全范围匹配。关联不等于已匹配，已有分数标需求版本/时间/过期状态。

任务租约45秒，每10秒短事务续租；dispatcher每3秒投递/恢复；最多3次执行；单次匹配Worker软/硬时限7140/7200秒，超时/中断经租约恢复或明确失败。重复投递条件领取，提交锁任务行并核对run_version；旧执行不能覆盖新执行。恢复后已提交条目保留，只继续待处理条目。断线不自动重做业务，创建幂等重试返回原记录。

## 限制

JD可能漏抽，原文/手工流程和生效必填拦截保留；仅纯文本JD，不导入岗位文档文件。复杂否定、技能同义词、学历/日期、中文数字和技能时间等按保守规则待核对，未承诺覆盖所有自然语言。大规模吞吐/长期负载未评测；启动范围快照和结果排序目前在本机内存及MySQL处理，无静默截断或top-k冒充全范围。保留历史包含业务事实，沿用本机受保护数据目录/数据库，不代表无限保留或公开部署。第二阶段UI/标签体验优化仍按已审批决定暂缓；第四阶段聊天/测评/完整管理页未开展。
