## 1. 产品目标与交付边界

平台面向企业人才管理，以统一人才档案为核心，连接简历解析、档案维护、轻量测评、岗位需求、人才匹配及系统管理。长期面向 HR、员工、业务负责人、管理层和系统管理员，首版以 HR 的实际业务为中心。

V1 交付一条可实际运行、可解释、可验收的业务链路：简历或人工资料进入人才档案，测评结果补充档案，HR 创建有效岗位并发起人才匹配，匹配结果保留证据和历史版本，工作台展示真实业务统计，权限与审计覆盖全过程。

独立开发采用分阶段完成方式，但不能通过删除数据来源、权限校验或异常处理来制造表面闭环。优先完成业务，再按样本评测与真实反馈优化。

### 1.1 V1 功能范围

| 模块 | 本版交付 |
|---|---|
| 智能工作台 | 真实统计、任务状态、业务入口、按权限展示 |
| 简历智能筛选 | 默认候选人筛选工作区；岗位关联、已有匹配分、分类标签、疑似重复提示；单份/批量上传及 PDF/图片/DOCX 解析，独立导入与解析记录 |
| 人才画像档案 | 内外部统一管理，分类标签、语义检索、事实来源与测评历史；档案内单人/批量 RAG 问答、比较、条件查询与人数统计 |
| 岗位—人才匹配 | 统一建岗表单，支持 JD 自动回填、手工编辑及可选 AI 完善，岗位版本，规则与语义匹配，解释与历史结果 |
| 轻量智能测评 | 固定题库、试卷版本、分配、答题、规则评分、结果入档 |
| 系统管理 | 用户、部门、角色权限、菜单、数据范围、敏感字段控制、操作审计和 AI 任务记录 |

### 1.2 后续版本范围

完整招聘流程（面试邀约、Offer、入职）、岗位缺口预警、人才储备推荐、自适应测评、AI 面试、个性化培训、通用企业知识库、独立管理层智能问数、高级审计分析及通用 Agent 编排管理端延期。

管理层角色的权限接入基础在 V1 建立；管理层专属智能问数与高级分析页面不纳入首版。延期能力继续保留在路线图中，不能因此提前开发完整空模块。

## 2. 角色与权限

### 2.1 首版角色职责

| 角色 | 首版职责与边界 |
|---|---|
| HR / 招聘人员 | 在授权范围内管理简历、人才、岗位、测评及匹配结果 |
| 员工 | 查看本人获授权资料，参加分配给本人的测评，查看允许展示的成绩 |
| 业务负责人 | 查看授权岗位和匹配结果；完整用人需求协同、审批后续实现 |
| 系统管理员 | 管理账号、部门、角色、权限、菜单及日志；管理身份不自动代表拥有所有人才业务数据读取权 |
| 管理层（扩展角色） | 首版支持通过现有角色机制配置其权限；专属问数、高级分析功能后续接入，不默认授予管理员权限 |

### 2.2 权限模型与规则

1. 用户可以关联多个角色；角色关联功能权限，不在每个业务接口中写死固定角色名单。新增角色复用同一鉴权机制。
2. 功能权限、数据范围和敏感字段权限分别判断。能进入页面，不等于能读取任意记录或任意字段。
3. 内部员工支持本人、指定部门、全公司等基础范围；外部候选人的访问按负责 HR 或明确人才库授权判断。任何人员身份、应聘岗位、职业标签都不能自动授予访问权。
4. 外部候选人无本企业所属部门，不强行关联研发部等内部员工部门。其职业/当前或最近岗位标签、外部任职公司与经历、应聘岗位及负责 HR/人才库授权分别存储和展示；管理授权不伪装为候选人的任职部门。未明确授权的数据默认不开放。
5. 多角色在已获授的功能与范围内访问；无明确授权时拒绝。复杂显式拒绝优先级、跨集团继承及下属部门递归策略不纳入首版。
6. 认证、功能、记录范围、字段展示、原文件访问和下载均由后端执行；前端菜单隐藏只用于体验。
7. 用户被禁用、权限被撤销后，后续受保护请求应拒绝；不能仅依赖旧登录凭证中的静态角色继续访问。
8. 工作台统计、列表、详情、语义检索、单/批量档案问答及计数、匹配和日志查询遵循同一授权边界。不得通过汇总数量、搜索摘要或文件链接绕过限制。
9. 员工不能通过更换人才 ID 或任务 ID 查看他人档案和测评。外部候选人无登录账号也可建档；账号与人才实体分离。
10. 未来智能问数必须在可信后端落实查询范围和字段限制；自然语言输入与模型生成内容不能扩大用户权限。

审计日志从 V1 开始记录，未来可授权管理层查询已有历史。日志查看权限与账号管理权限分开；不提供普通用户编辑或删除审计记录的业务入口。

## 3. 核心业务流程

### 3.1 简历进入人才档案

HR 上传文件 → 建立批次和文件级任务 → 校验文件 → 提取文字/按页 OCR → 抽取并校验结构化字段 → 建档或提示疑似重复 → 异常核对与人工修正 → 可授权检索和匹配。

正常解析结果可以进入档案，入库不代表所有字段已获人工确认。缺失、冲突、识别不足字段保留明确标识；关键身份关联不可靠时不得盲目覆盖既有人才。单个文件失败不影响同批其他文件。

### 3.2 轻量测评补充档案

HR/获授权管理员维护题库与试卷 → 发布固定版本 → 分配给已绑定账号的员工 → 员工答题提交 → 程序规则评分 → 保存成绩与答题记录 → 在本人对应档案展示有来源、有时间的结果。

### 3.3 岗位创建与人才匹配

岗位创建只有一个入口、一套可编辑表单，不按资料准备方式拆成不同页签。已有 JD 可粘贴到输入框，系统自动提取并回填岗位字段；只有部分需求时，可填写已知字段或自然语言描述，选择 AI 辅助完善草稿；也可直接手工填写。上述方式可以在同一页面混合使用。

HR 保存草稿 → 补齐必填字段与结构化要求 → HR 确认并保存有效岗位版本 → 按需手动发起匹配 → 硬条件判断与语义召回/排序 → 展示证据、缺口和未知项 → 保存结果。

已有完整 JD 粘贴后自动提取并回填同一表单，HR 无需切换模式或重复录入。自动回填不能无提示覆盖已有人工修改；存在冲突时保留差异并供 HR 核对。提取失败保留原文与已有字段，可重试或手工完成。手动填写并保存岗位不依赖 AI 调用；自动提取和 AI 完善为同一表单内的辅助能力。岗位文档导入的格式在页面/API 设计中明确。

保存岗位不会自动启动匹配。草稿和已停用岗位不能发起新匹配。

## 4. 岗位状态、字段与版本规则

### 4.1 状态

| 状态 | 可执行操作 | 限制 |
|---|---|---|
| 草稿 | 暂存、编辑、生成/导入 JD、补齐信息、确认生效 | 允许暂缺业务必填项；不能用于匹配 |
| 有效 | 查看、发起匹配、基于当前版本编辑、停用 | 生效版本已通过后端校验并经 HR 确认 |
| 已停用 | 查看历史、基于历史版本重新编辑并确认生效 | 不能发起新匹配；历史记录保留 |

有效岗位的修改先作为待保存草稿处理；只有重新校验、确认后才产生新的有效版本。未确认的编辑不改变原有效版本；停用前后的历史匹配不被覆盖。岗位停用后，已开始的任务按启动时快照完成并标注当前岗位状态，不再接受新匹配任务。

### 4.2 字段与校验

| 信息 | 草稿 | 保存有效岗位版本 |
|---|---|---|
| 岗位名称 | 可暂缺 | 必填 |
| 所属/管理部门 | 可暂缺 | 必填，用于业务归属与授权 |
| 工作地点 | 可暂缺 | 必填 |
| 薪资 | 可暂缺 | 必填 |
| 岗位职责 | 可暂缺 | 必填 |
| 任职要求及结构化匹配条件 | 可暂缺 | 必须明确并经 HR 确认；不限项显式表达“无此限制” |
| 福利 | 选填 | 选填；没有时省略，不显示“待补充” |

薪资、地点为用户明确要求；岗位名称、部门、职责和要求为本版补齐的实施规则。薪资不得由 AI 凭空补写；填写区间时需明确币种、计薪周期且下限不高于上限。是否允许“面议”等枚举值在表单设计时明确，不能用空字符串或占位符绕过必填。地点需填写可理解的实际安排，远程岗位可明确标注远程及适用区域。

AI 可根据需求组织正式 JD、润色职责与提出建议；未提供的企业事实不编造。AI 建议的技能、经验或学历限制，须由 HR 确认后才能成为匹配条件。缺失的必填信息通过表单提示补齐，不能保存为有效岗位。

JD 正文与结构化条件需一致；例如“Docker 优先”不能被保存成必备技能。系统展示两者供 HR 核对；不一致时要求修正或明确确认一致的条件版本，不默默采用模型推断。

## 5. 功能需求与验收

P0 是首版主链路优先建设项；P1 是首版后续阶段建设项，仍属于 V1 验收范围；P2 属于未来版本。内部阶段交付不代表可以跳过 P1 宣称 V1 全部完成。

### 5.1 智能工作台

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| DASH-01 | 角色导航与业务入口 | P0 | 仅展示获授权入口，直接访问接口仍需鉴权 |
| DASH-02 | 人才总数及内外部分类 | P0 | 与同授权范围的数据库统计一致 |
| DASH-03 | 解析批次、待处理与失败统计 | P0 | 可跳转到对应任务列表 |
| DASH-04 | 岗位、匹配任务与最近结果 | P0 | 数据真实，岗位状态可区分 |
| DASH-05 | 测评待参与、完成与任务统计 | P1 | 员工只看到本人，HR 受范围限制 |
| DASH-06 | 操作与 AI 执行概览 | P1 | 可查询详情；空态明确，不伪造实时数据 |

### 5.2 简历智能筛选、解析与 OCR

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| RES-01 | 单份/批量上传及批次管理 | P0 | 每个文件有独立状态，批次汇总可对账 |
| RES-02 | 文本 PDF、扫描 PDF、混合 PDF、JPG/JPEG、PNG、DOCX 解析 | P0 | 均有实际处理通路；不以仅支持文本 PDF 代替 OCR |
| RES-03 | 文字提取与 OCR | P0 | PDF 按页选择处理方式，覆盖多页扫描及图文混合；识别不足可提示 |
| RES-04 | 结构化字段抽取 | P0 | 姓名、联系方式、教育、经历、项目、技能、证书等可查看；缺失不编造 |
| RES-05 | 状态、异常与重试 | P0 | 可查询待处理/处理中/成功/需核对/失败，失败原因可理解，重试有边界 |
| RES-06 | 进入统一人才档案并关联来源 | P0 | 保留原文件、任务和结果关联，重试不重复生成同一成果 |
| RES-07 | 来源查看与人工修正 | P0 | 可查原文/原文件；人工修正不被后续解析无提示覆盖 |
| RES-08 | 条件检索、筛选、排序 | P0 | 按身份、技能、学历、经验等检索，遵循授权范围 |
| RES-09 | 疑似重复提示与对比 | P1 | 展示身份线索、履历对比及来源，可标记同一人待关联或排除；不凭姓名/向量相似度自动合并，不纳入通用档案合并引擎 |
| RES-10 | 批次进度和历史记录 | P1 | 可逐项查看处理结果及重试记录 |
| RES-11 | 默认候选人筛选工作区 | P0 | 以候选人为行，展示岗位关联、当前所选岗位下已有匹配分、核心标签与资料状态，支持筛选和跳转画像 |
| RES-12 | 导入与解析记录页签 | P0 | 独立呈现文件/批次、处理中、失败原因及重试；不能以任务列表代替候选人筛选 |

筛选规则：默认可展示未关联岗位的候选人；选择具体岗位后按显式岗位关联查看候选人及该岗位的匹配结果。关联岗位不等于已发起匹配；未运行显示“未匹配”。已有分数注明岗位版本和生成时间，岗位或档案更新后显示旧结果需更新，不能静默当成当前分数。职业标签不等于实际应聘岗位。同一人多份简历在候选人列表按人才 ID 去重，文件任务仍分别保留；未可靠识别身份时提示疑似重复，不能为追求去重而错误合并。

OCR 边界：必须实现常见清晰打印简历的识别；严重模糊、反光、遮挡、手写及复杂版式可能导致识别不足。系统应提示核对或失败，不承诺任意质量、任意格式均完整准确。复杂案例也应有可观察的结果，不能静默成功后写入明显无效字段。

文字识别与业务字段抽取分别评估，避免把 OCR 读错归因于字段提示词，或把字段抽取错误视为 OCR 错误。不得使用模型自行声称的置信度替代真实正确率评测。

文件大小、页数、批次文件数等上限应在实现前定义为配置并显示在上传处；不合规、损坏、加密无法读取或不支持的文件给出明确反馈。具体上限记录于实现配置与验收说明。

### 5.3 人才画像档案

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| TAL-01 | 内外部统一人才实体与身份分类 | P0 | 同一主实体可挂接不同来源；外部候选人无需账号 |
| TAL-02 | 基础资料、教育、经历、项目、技能与证书详情 | P0 | 缺失项明确，事实与 AI 推断分开 |
| TAL-03 | 来源、时间与人工修正标记 | P0 | 能追踪来自何份文件或哪次人工维护 |
| TAL-10 | 分类标签与来源 | P0 | 按技术、项目、行业经历、证书等分类，区分事实/推断/测评及人工确认状态；标签数量由有效证据决定，不凭简历推算软素质 |
| TAL-04 | 测评历史与分项结果 | P0 | 有试卷/规则版本、完成时间，不覆盖历史 |
| TAL-05 | 人工建档与补充修改 | P0 | 无简历的内部员工也可建档并绑定账号 |
| TAL-06 | 关键变更历史 | P1 | 可查看操作者、时间、修改摘要 |
| TAL-07 | 自然语言语义检索人才 | P1 | 结果基于授权档案并可追溯证据 |
| TAL-08 | 有限能力雷达图 | P1 | 仅展示已测量且可比较的分项，缺失明确“未测评”，不从简历推算五维分数 |
| TAL-09 | 统一档案 AI 聊天入口 | P0 | 人才画像档案内提供统一聊天入口，支持查人、单人问答、多人比较与连续追问，无需切换功能模式；回答有逐人证据引用 |
| TAL-11 | 档案条件查询与人数统计 | P0 | 同一问答入口内理解筛选条件，展示查询范围、条件与去重人数，不能把向量 top-k 当总数 |
| TAL-12 | 问答范围与会话 | P0 | 当前档案、选中人才和筛选条件可带入会话；AI 识别意图并明确显示查询范围，歧义时对话澄清；范围变化需明确提示/确认，不静默扩大 |

人才详情可展示事实标签与摘要，但不得将“简历提到某技能”直接写成该技能已通过能力测评。测评分数仅代表指定题库、指定时间测得的表现。

### 5.3.1 档案问答交互与回答规则

档案问答属于人才画像档案模块，独立管理层智能问数继续延期。后端按问题选择结构化查询、检索或组合处理，不让 HR 为此切换产品模块，不要求 HR 选择 SQL/RAG 技术模式。

- 单档案：打开人才详情，在同页问答面板提问，例如“是否有大规模模型落地的完整经验？”。回答应说明支持的环节、角色和缺失证据；涉及规模的结论须有可核查量化/业务规模依据，不仅凭技能标签断言“具备”。
- 统一聊天：HR 可直接表达“找有 RAG 经验的人”“符合条件的有多少人”“比较这几位”等需求。系统结合对话和当前页面识别对象与意图，执行查询/检索并整理回答，不要求先选单人、批量或统计模式。
- 多人范围：勾选人才、当前筛选条件可作为聊天上下文；明确要求全库查询时仅使用全部授权范围。显示本次范围、人数和身份条件；不清楚“这些人”指谁时在对话中澄清。空选集不自动升级为全库。每个人的证据归属于本人，不能把甲的经历当乙的能力。
- 条件人数：例如“有多少位本科、3 年以上经验的 Python 外部候选人？”，展示被理解的条件，后端对授权数据完整过滤并按人才 ID 去重计数；条件有歧义先澄清，不能暗自改写“以上/超过”“本科/本科及以上”。
- 语义条件：例如“有完整大模型落地经验的候选人有多少？”，须说明判定依据、已评估范围、有证据支持和信息不足的数量。未覆盖全部指定范围或存在检索截断时，明确为当前找到的数量，不能宣称全量精确总数。
- 引用需关联人才、来源文件/记录、可定位的页码或片段及版本。引用可点击核对；结构化计数提供条件、范围及结果明细，不强行伪造文档引用。
- 追问沿用明确的人才范围，可重新查询当前有效资料；旧回答记录查询时间/版本，不把过期上下文当最新事实。超时、索引未就绪或证据缺失时如实提示，不伪造回答。
- 问答只读，不通过聊天直接修改档案、合并人才或作录用决策；嵌入简历中的指令不改变权限、范围或回答规则。

标签与向量索引分别承担可解释的分类展示与语义召回职责。简历处理、画像、问答及匹配通过统一人才 ID 和来源版本相连；向量库不替代业务主数据和权限系统。

## 6. 异常、状态与一致性规则

| 场景 | 系统行为 |
|---|---|
| AI 生成 JD 超时或格式错误 | 保留用户原输入和已有编辑，显示失败；可重试或改用手动填写 |
| OCR/字段抽取部分不足 | 保留可用信息和来源，标记需核对；不把缺失内容补写成事实 |
| 文件损坏或不支持 | 标记失败并说明原因；批次其他任务继续 |
| 重复请求或任务重试 | 用业务唯一标识/状态约束防止重复建档、成绩与同次结果落库 |
| 请求超时但结果可能已保存 | 先查询任务状态，再决定是否重试；不盲目重复执行 |
| 超时后的迟到结果 | 按任务执行版本判断是否仍有效，不覆盖较新结果或人工修正 |
| 同时编辑同一档案/岗位 | 检测版本冲突，提示刷新或重新确认，不能静默覆盖 |
| 匹配期间源信息更新 | 使用启动时绑定的有效快照；后续重跑产生新记录 |
| 匹配期间授权被撤销 | 结果读取重新鉴权；运行中的数据访问检查有效权限，不能凭旧任务绕过新限制 |
| 档案问答超时/无证据/统计条件歧义 | 保留问题与明确范围，提示重试/证据不足/条件澄清，不生成虚假结论或人数 |
| 服务重启 | 已保存业务状态和任务记录可查询；明确恢复/失败/重试状态，不长期假装处理中 |

解析任务可采用待处理、处理中、成功、需核对、失败；匹配任务至少有待处理、处理中、成功、失败。业务状态、技术执行状态与访问拒绝原因分别记录，不能用一个 success 掩盖业务未完成。

## 7. 核心数据对象与来源原则

| 对象 | 职责和关联 |
|---|---|
| 人才主实体与身份 | 统一内外部人才；以稳定人才 ID 关联简历、测评和匹配 |
| 登录账号 | 认证、角色、部门，可选绑定人才；候选人不强制创建账号 |
| 部门、角色、功能权限、数据授权 | 支撑扩展角色与可核查的数据范围 |
| 简历文件、批次、解析任务、抽取结果 | 保留原始文件、处理状态、来源、版本及人工修正标记 |
| 档案事实、标签与变更 | 标签分类、来源证据、确认状态；区分文件事实、人工维护、AI 推断和测评结果 |
| 候选人管理与岗位关联 | 职业标签、外部任职信息、负责 HR/人才库授权、实际岗位关联分别建模；无内部部门 |
| 档案问答会话、消息与证据引用 | 问题、范围快照、条件、查询时间、回答、逐人来源版本及失败状态 |
| 题目、试卷版本、测评任务、答题、成绩 | 固定评分依据，保留时间和历史 |
| 岗位、草稿、有效版本、结构化要求 | 正文与匹配条件绑定同一确认版本，保留薪资和地点 |
| 匹配任务、人才/岗位快照、结果 | 可复盘当时依据及规则版本，不被源数据更新改写 |
| 审计日志、AI 任务日志 | 关联操作者、目标对象、任务、时间、动作与结果 |

以上为概念模型，不强制每个对象独占一张表。表结构、接口字段、枚举和索引在详细设计中确定。

历史记录按当时业务事实保留，不等于无限期保留个人信息。删除、更正和保留期限策略应覆盖原文件、主库、索引、快照与日志中的个人信息；通过受控脱敏/清理兼顾追溯，不以审计历史为由保留全部敏感正文。

未来招聘、培训、储备、缺口等业务通过稳定人才 ID、岗位 ID 和组织 ID 扩展，不把未来流程状态塞入一个万能档案字段。

## 8. 技术边界与质量要求

以 FastAPI、MySQL、LangGraph 为技术方向，前端优先 Vue；在详细设计中选择库、组件和版本。LangGraph 用于确有需要的多步骤/有状态流程，不要求每个普通业务操作都经过 Agent。

文档解析与 OCR 为首版必须能力；AI 用于字段抽取、可选 JD 生成/理解、档案检索问答和匹配解释；代码负责鉴权、必填校验、状态控制、评分规则与持久化。用户可在 AI 不可用时继续手工维护档案、岗位等基础业务。

语义匹配必须有可评测实现；Milvus、Redis/Celery、对象存储等按负载与部署需要引入，不以组件数量作为交付目标。若使用向量索引，应关联人才 ID 与有效版本，落实更新、删除与权限同步，不能依赖前端过滤检索结果。

| 质量要求 | 验收方式 |
|---|---|
| 安全 | 验证跨用户、跨部门、直接 API、原文件及敏感字段访问均不能越权 |
| 可靠性 | 混合成功失败批次、重复提交、超时、重启及版本冲突均有明确结果 |
| 可解释性 | 抽取有来源、测评有规则、匹配有命中/缺口/未知和证据 |
| 可维护性 | 分层清晰，统一响应和错误约定，关键业务接口具有必要自动化验证 |
| 性能 | 记录样本规模、硬件/模型配置、耗时和失败率，形成可复现首轮基线 |
| 解析评测 | 小型标注样本按文本 PDF、扫描 PDF、混合 PDF、图片、DOCX 分组，统计 OCR 与字段抽取错误 |
| 档案问答评测 | 验证来源命中、引用正确、回答忠实度、单/多人隔离；数据库计数与人工可复现条件结果一致，语义判定记录覆盖率和未知项 |
| 匹配评测 | 以人工标注的岗位—人才样本核对硬条件、排序合理性与解释证据 |

不预先虚构准确率或时延数字；首轮评测报告必须记录指标定义、样本、实际结果与不足，再形成后续质量目标。流程验收通过不等同于模型效果已达到企业级精度。

| E2E-10 | 草稿/停用岗位发起匹配 | 后端拒绝；有效岗位保存后不会自动启动匹配 |
| E2E-11 | 有效岗位匹配多名人才 | 满足/不满足/信息不足明确，语义排序和依据可核查，结果持久化 |
| E2E-12 | 修改岗位/档案后重跑匹配 | 生成新结果，旧岗位/人才/规则快照和解释仍可复盘 |

| E2E-17 | 工作台、列表与数据库对账 | 同一授权范围数据一致，无硬编码演示经营指标 |

| E2E-19 | 候选人筛选与解析记录切换 | 默认候选人列表；过滤、岗位关联、未匹配状态、历史分数版本及跳转画像可用；任务页按文件展示 |
| E2E-20 | 外部候选人建档与权限 | 无内部部门，职业标签/任职/应聘岗位/管理授权分开；负责人范围不因岗位标签自动扩大 |
| E2E-21 | 单档案问落地经验并追问 | 结论受证据支持、规模与参与环节明确；引用定位可用，证据不足不强判 |
| E2E-22 | 同一聊天内查人、问答、比较与追问 | 无需预选单人/批量/统计模式；范围清晰、歧义对话澄清、空选不扩大；逐人引用不串人，越权资料不进入上下文 |
| E2E-23 | 条件人数查询与语义人数问题 | 结构化条件按人才 ID 去重计数准确；歧义澄清，语义查询说明覆盖范围、未知项，无 top-k 冒充总数 |
| E2E-24 | 疑似重复资料对比 | 展示可信身份线索和来源，允许排除或标记待关联；不自动合并不同人 |

V1 完成条件：P0、P1 按本表与功能表验收通过；交付部署说明、必要测试记录及首轮模型效果基线报告。未完成项必须如实标注，不能用原型效果替代实际实现。

## 10. 开发阶段与未来演进

| 阶段 | 建设重点 | 可检查成果 |
|---|---|---|
| 阶段一 | 用户、权限、部门归属、文件与任务基础、人才主实体 | 身份与数据范围可验证，基础建档可运行 |
| 阶段二 | PDF/图片 OCR、DOCX、结构化抽取、分类标签、候选人筛选与查重对比 | 多格式简历入档，筛选与任务视角分开，批次失败受控 |
| 阶段三 | 统一建岗表单、JD 自动回填与 AI 完善、状态、版本及匹配 | 从有效岗位到可解释历史结果的完整链路 |
| 阶段四 | 档案内单/批量问答与计数、轻量测评、画像、工作台与管理页面 | 问答有引用、范围和计数依据，测评入档及 P1 补齐 |
| 阶段五 | 权限回归、异常场景、样本评测与部署 | 验收记录、效果基线、可复现部署 |

各阶段持续落实日志、鉴权与异常处理，不能最后才补安全边界。阶段顺序可按依赖细调，不改变 V1 功能范围，不在本稿承诺工期。

V1.1 候选方向：用人需求协同、岗位缺口、储备池推荐、基础招聘进度。V2 候选方向：高级测评、培训成长、管理层自然语言问数、高级审计分析及企业知识问答。具体排期与新增范围另行确认。

## 11. 需求冻结与变更管理

本文件定义 V1 的产品范围、业务流程、功能规则和验收标准。李玉杰已于 2026-11-04 明确确认冻结，作为 V1.0 开发与验收的需求基线。

冻结后新增或调整需求应记录变更内容、业务目的、影响范围、依赖及验收条件，经李玉杰确认进入当前版或后续版后更新基线。不得在实施过程中静默扩大或删减功能范围。

数据库与接口、页面布局、薪资枚举细节、文件限制数值、模型/OCR 组件、算法参数及调度组件在详细设计与实现配置中明确。实现设计应满足本文件的业务规则；涉及功能范围变化时按需求变更处理。

开发与验收以本冻结文档为准。现有交互原型用于布局与流程参考；统一档案 AI 聊天入口和统一建岗表单按本文件实现，原型无需继续补改，也不作为进入详细设计的前置条件。
